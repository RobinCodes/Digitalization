# Audit — September 2026

Two passes over `server.js`, `index.html` and `devtools.html` looking for real defects rather
than style. **Twenty-seven findings**, all fixed and covered by the suite (`node Tests/run.js`,
now **294 assertions**). Each entry says what was wrong, why it mattered, and what changed.

Pass one (§1–14) was a general sweep. Pass two (§15–27) was a pre-hosting review: everything an
anonymous or merely-signed-in visitor can reach, and everything that has to hold up when the
server runs unattended for weeks.

---

## Security

### 1 · `/api/file` served `data.txt` — anonymous metadata disclosure (HIGH)

`GET /api/file?path=Some/Folder/data.txt` returned the folder's raw `data.txt`. That file is
not note content: it holds every note in the folder's `see-allow`, `read-allow` and `owners`
lists. Anyone, signed out, could read the account names of your whitelisted members and the
access configuration of notes they cannot otherwise see. The `/data/` route already blocked
`data.txt` explicitly; `/api/file` never got the same guard.

Fixed: `/api/file` returns 404 for any path ending in `data.txt`, matching `/data/`.

### 2 · The static-file guard was case-sensitive (HIGH on Windows/macOS)

`isProtectedStatic()` compared the last path segment against a lowercase allowlist with
`Set.has()`. Windows and macOS filesystems are case-insensitive, so **`GET /ADMINS.JSON`
walked straight past the guard and served the credential store** — salts and scrypt hashes for
every admin. Same for `/Users.json`, `/Chats.json`, and so on.

Fixed: the comparison is now case-insensitive, and the directory guard (`tests`,
`node_modules`, `Uploads`) is too.

### 3 · `note-discussions.json` was not protected (HIGH)

The per-note discussion store was added later than the protected-file list and never added to
it. `GET /note-discussions.json` served **every discussion thread on every note**, including
threads on members-only and whitelist-restricted notes, to an anonymous visitor.

Fixed: `note-discussions.json` (and `changelog.json`, and the two new stores) are on the list.

### 4 · `safePath()` decoded twice

`url.parse(req.url, true)` already percent-decodes query values, but `safePath()` decoded
again. Two consequences:

- A real filename containing `%` (e.g. `100%.tex`) either resolved to the wrong file or threw
  `URIError` and 403'd.
- The `/data/` route — which serves images, embedded media and downloads — passed the still-
  **encoded** pathname into `canViewNote`. The grant key is built from that path, but
  `/api/access/respond` writes the grant with the **decoded** path, so for any note whose path
  contains a space or an accent the two never matched: a user who had been granted access could
  read the source and the compiled PDF but still got 403 on the note's images and downloads.

Fixed: `safePath()` no longer decodes; the four pathname-derived call sites decode once, via a
new `decPath()`, so the file lookup, the visibility check and the grant key all agree.

### 5 · `/api/access/respond` did not re-check authority

Responding to a read request only required being a participant in the conversation the request
card sits in. In practice that is the note's owner — but if the note's owners changed after the
request was sent, the *former* owner could still grant access to it.

Fixed: the responder must currently be an admin or one of the note's recipients.

### 6 · Two admin endpoints read unbounded request bodies

`/api/changelog/add` and `/api/changelog/delete` accumulated the whole body in memory with no
cap, unlike every other POST route. Admin-only, so low severity, but it is the one way to make
the process allocate without limit.

Fixed: 256 KB and 8 KB caps respectively.

## Availability

### 7 · A LaTeX compile froze the entire server (HIGH)

`/api/compile` ran `spawnSync(pdflatex)` **twice**, each with a 120-second timeout, plus a third
synchronous `pdflatex --version` probe on every request. `spawnSync` blocks the Node event
loop, so for the whole duration of a compile the server answered **nothing** — no page loads,
no chat, no other note. One visitor opening an uncached note stalled every other visitor, and
a handful of concurrent requests was a trivial denial of service.

Fixed:

- `compileTexSync` → `async compileTex`, built on `spawn` + promises. The request handler
  awaits it, so the event loop stays free.
- The `--version` probe now happens **once**, at start-up (`PDFLATEX_OK`).
- Output buffering is capped at 4 MB per run so a runaway log cannot exhaust memory.
- Concurrent compiles are queued at `COMPILE_CONCURRENCY` (default 2) — each run is a real
  process, and a burst of readers should not fork the machine to death.

Measured on the real archive: during a 1.5 s compile, unrelated requests answered in 1–15 ms
(previously they waited for the full compile), and three concurrent compiles no longer stall
`/api/tree`.

### 8 · `/api/tree` re-read the same files O(N) times

Building the tree annotates each note with whether the current viewer may open it. That check
parsed the note's folder `data.txt` **and its counterpart's** from disk, and called
`loadGrants()` — a fresh `grants.json` read — **once per note**. An archive of N notes cost
roughly 3N synchronous file reads on every tree request, and the tree is requested on every
page load and language switch.

Fixed: `parseDataTxt` and `loadGrants` are memoised on `(mtime, size)`, so an edit is still
picked up immediately but a request re-reads nothing. Read-modify-write paths take an explicit
mutable copy (`parseDataTxtMutable`) so they cannot corrupt the shared cache, and every write
goes through `writeDataTxt`, which invalidates the memo.

### 9 · Two in-memory maps never shrank

`SESSIONS` only dropped an expired token when that same token was presented again, and the
rate-limiter map kept one permanent entry per client IP per bucket. On a long-running server
both grew without bound.

Fixed: a ten-minute sweep drops expired sessions and elapsed rate-limit windows.

## Data integrity

### 10 · `data.txt` writes were not atomic

Every other state file (`users`, `settings`, `grants`, `chats`, `changelog`) writes via
temp-file + rename. The four routes that rewrite a folder's `data.txt` — `/api/admin/datatxt`,
`/api/admin/note`, `/api/admin/folder/meta`, `/api/admin/note/delete`, `/api/note/manage` —
used a plain `writeFileSync`. A crash or a full disk mid-write loses the metadata for every
note in that folder.

Fixed: all of them go through `writeDataTxt()`, which writes atomically.

### 11 · Invalid timetable slots were coerced, not dropped *(found by the new tests)*

A slot whose weekday was out of range fell back to Monday, and one whose period no longer
existed fell back to the first period. Deleting a period therefore did not delete its lessons —
it moved them, inventing a phantom Monday-period-1 lesson that then seeded every day logged
for that weekday.

Fixed: a slot that does not fully resolve is dropped.

### 12 · Turning off the A/B week cycle hid the week-B lessons

Week parity is 0 when no cycle is configured, and slots were filtered with
`slot.week === parity + 1` — which matches week-A slots but never week-B ones. Switching a
timetable from alternating back to a single week silently deleted half of it from view.

Fixed: with no cycle configured, a slot's week tag is ignored and every slot shows. (Both
server and client.)

## UX

### 13 · The DevTools date picker leaked listeners and fired no event

`makeDatePicker()` registered its own `document` click handler per instance, holding a
reference to its wrapper forever. With four static pickers that was invisible; the timetable's
holiday rows are rebuilt on every edit, which would have leaked one listener per row per
keystroke. Picking a date also assigned `input.value` directly, which fires nothing — so no
caller could react to a pick.

Fixed: one shared outside-click handler closes any open popover, and picking a date (or
Today/Clear) dispatches a `change` event. The day editor uses that to re-seed itself when you
change the date.

### 14 · The media viewer was hard-wired to `/data/`

`openMediaModal` built its URL from `'/data/' + item.path`, so nothing outside the note tree
could use it.

Fixed: split into `openMediaUrl(src, name, ext, kind, downloadUrl)` with `openMediaModal` as a
thin wrapper. Day-log attachments reuse the same viewer, and downloads keep their real
filename instead of the storage id.

# Pass two — the pre-hosting review

Everything below is reachable by someone who is not you. The theme of the pass is that the
access model was enforced carefully on the routes built for it (`/api/tree`, `/api/file`,
`/data/`) and less carefully on the routes built for something else.

## Security

### 15 · `/api/precompile/status` listed every note in the archive (HIGH)

`autoPrecompile` walks `Data/` and `DataHU/` at start-up and records one entry per `.tex` file
in `preStatus`, keyed `"<lang>:<full/relative/path>"`. The status endpoint returned that whole
map **to anyone**, with no session at all.

So the one route that exists to say "the queue is 12 deep" was also handing an anonymous
visitor the folder and filename of every members-only and whitelist-restricted note on the
site — the very thing `/api/tree` filters out node by node. Finding §1 in pass one closed a
disclosure of *who* may read a restricted note; this was a disclosure of *which notes exist*.

Fixed: `queue` and `running` stay public (they are all the Settings panel reads). The per-note
map is returned only to an admin session.

### 16 · `/api/precompile/folder` was an anonymous, unmetered job queue (MEDIUM)

Its sibling `/api/precompile/start` requires an admin. This one required nothing. A single
anonymous POST with `folderPath: ""` walked the entire archive and queued a `pdflatex` run for
**every note in it, restricted ones included** — up to the 500-deep backlog cap, repeatable 60
times per five minutes.

That is both a cheap way to keep the machine busy indefinitely and a way to force private notes
through the compiler and into the render cache.

Fixed: the route stays public, because the Settings panel's *Compile all now* is a visitor
feature and warming the cache for the notes you can read is the point of it. But it now queues
only notes that pass `canViewNote` for the caller, and the rate limit is 10 per five minutes —
one call can still enqueue hundreds of jobs, so the call itself has to be rare.

### 17 · `/api/admin/login` had no brute-force limit at all (HIGH)

`/api/login` was limited to 20 attempts per ten minutes. `/api/admin/login` — the same
credential, the route that hands out the token which can rewrite every note's access rules —
had no limit whatsoever. A probe ran 40 wrong passwords with no slow-down and no lockout; the
number could as easily have been 40 million.

Fixed: 20 attempts per ten minutes, in its **own** bucket rather than sharing the site's. A
shared bucket is marginally stricter but means any member fumbling their password locks the
owner out of DevTools; 20 admin guesses per ten minutes already ends brute force as an attack.

### 18 · `/api/access/info` named a hidden note's owners to anyone signed in (MEDIUM)

The handler computed `applicable` correctly — it checked the see-gate — and then returned
`recipients: requestRecipients(path)` **unconditionally**, for any path the caller cared to
name. A signed-in member could therefore read back the owner list of a note they are not
allowed to know exists.

Fixed: `recipients` is returned only when a request is actually possible (or already pending).
A request-tier note is visible to everyone by design, so naming its owners there still works —
that is the whole purpose of the card.

### 19 · An access request could name a note the sender cannot see (LOW)

`/api/access/request` checked that the note *takes* requests but never that the sender may see
it, so a member outside the see-whitelist could post a request card for a hidden note. That
leaks the note's path to its owners as an apparently legitimate request, and hands the sender
its display label in the reply.

Fixed: the see-gate is checked, and the refusal is worded identically to the "this note does
not require a request" case so the two are not distinguishable.

### 20 · A members-only day's attachments answered 403, not 404 (LOW)

The day log is documented as answering an anonymous request for a members-only day exactly as
it answers a request for a date that was never logged — and `/api/day`, `/api/days` and
`/api/days/index` all do. The attachment route did not: it returned **403** for a real
members-only day and **404** for an unknown one, so the status code alone confirmed the day
exists.

Fixed: 404 in both cases.

### 21 · `/api/admin/users` accepted any username and any password (MEDIUM)

Public sign-up enforces 3–32 characters of `[A-Za-z0-9_.-]` and an 8-character password.
`make-admin.js` and `make-user.js` enforce the same. The admin route enforced neither — it
accepted `{ username: "<img src=x onerror=…>", password: "a" }` and wrote it to `users.json`.

The account name then flows into every other member's chat list, participant picker and
note-owner field. Those render sites all escape correctly today, so this was a loaded gun
rather than a fired one — but a one-character password on a real account is a defect on its
own.

Fixed: one `USERNAME_RE` / `MIN_PASSWORD` pair, applied wherever an account is created.

### 22 · Sessions outlived the accounts and passwords behind them (MEDIUM)

`SESSIONS` is an in-memory token map, and nothing ever consulted `users.json` again after
sign-in. So:

- **Deleting an account did not sign it out.** You remove someone from `users.json` and their
  browser keeps working for up to eight hours — reading members-only notes, posting in chats,
  editing the metadata of notes they own. "Remove this person" has to mean it immediately.
- **Changing a password did not sign out anyone else.** The usual reason to change a password
  is that someone else has it; leaving their session alive changes nothing for them.

Fixed: a `revokeSessions(username, exceptToken)` helper, called on account deletion, on an
admin password reset, and on a self-service password change — the last one sparing the caller's
own token so they are not logged out of the tab they are typing in.

### 23 · A section header in `data.txt` was written unescaped (defence in depth)

Values are flattened with a newline-to-space replace before being written, which is what stops
a note owner injecting a second `[Section]` through the description field and rewriting a
neighbouring note's access rules — verified, and now pinned by a test. The **section name**
itself had no such treatment. Every current caller derives it from an on-disk filename, so
there is no path to it today; on Linux a filename may legally contain a newline.

Fixed: newlines and `]` are stripped from the section name too.

### 24 · No `Strict-Transport-Security` (hardening)

Nothing told a browser to stay on HTTPS, so the first request of every visit was downgradeable.

Fixed: `max-age=15552000; includeSubDomains`, emitted **only** when the connection really is
HTTPS — direct TLS, or a trusted proxy saying so via `X-Forwarded-Proto`. Sending it over plain
HTTP would pin a local or dev host to a scheme it cannot serve. `HSTS_MAX_AGE=0` opts out.

## Availability

### 25 · The background precompile queue could wedge permanently (HIGH)

`runNextPrecompile` spawned `pdflatex` with Node's default `stdio: 'pipe'` and then never read
`stdout` or `stderr`. Node's child streams start paused, so nothing drains them: once the child
writes more than the OS pipe buffer it **blocks on write forever**. `preRunning` stays `true`,
and every remaining note in the queue is never compiled for the lifetime of the process — plus
two orphaned `pdflatex` processes and a leaked temp directory per stuck note.

The on-demand path (`runPdflatexOnce`) attaches `data` handlers and so drains correctly; only
the background path had this. It also had no timeout, so a genuinely stuck LaTeX run had the
same effect.

Reproduced with a child writing 2 MB to an unread pipe: it never exits. The threshold on a real
note depends on how chatty the document is — one note in this archive produces 4 KB, while a
long document with font warnings or a MiKTeX package install produces far more — so this is a
latent hang that gets likelier as the archive grows, not one that fires on every note.

Fixed: `stdio: 'ignore'` — the output was never used, only the presence of the `.pdf` is
checked — plus a `PRECOMPILE_TIMEOUT_MS` watchdog (default 180 s) and a `settled` guard so the
queue advances exactly once per note however the run ends. Verified on the real archive: 51 of
51 notes precompiled, queue drained to empty, no errors.

### 26 · `/api/compile` was unauthenticated, unmetered and unbounded (MEDIUM)

A cache miss forks two real `pdflatex` processes. The route had no rate limit, and the queue in
front of `COMPILE_CONCURRENCY` was unbounded — so a burst parked an unbounded number of pending
requests, each holding a socket and a promise, waiting for a slot minutes away.

Fixed: 90 requests per five minutes per IP (a cache hit is answered before the queue is
touched, so ordinary reading never approaches it), and `COMPILE_QUEUE_MAX` (default 24) waiters,
past which the server answers 503 with a "try again in a moment" message rather than timing out
slowly. The slot is acquired outside the `try`, so a refusal cannot run the `finally` and
release a slot that was never taken.

Measured after the fix: 8 concurrent uncached compiles finished in 6.4 s while unrelated
requests answered in 0–34 ms, and a cached compile straight after the burst returned in 3 ms —
so no slot leaked.

## UX

### 27 · The PDF viewer swallowed the server's explanation

`if (!res.ok) throw` discarded the JSON body on every refusal. So "This note is available to
signed-in members only." — and now also the rate-limit and busy messages — reached the reader as
`Server error: HTTP 403`. The split-pane viewer already read the body; the main one did not.

Fixed: the main viewer reads `log` out of a JSON error response, falling back to the status code
only when there is no message.

## Not changed (deliberately) — both passes

- **Article pages keep `'unsafe-inline'` in `script-src`.** Unchanged from the previous audit
  and for the same reason: articles are admin-authored HTML documents that legitimately carry
  inline handlers. The app shell keeps its strict per-request nonce.
- **State files are read-modify-written without locking.** Each handler does its load → mutate →
  save synchronously inside one `req.on('end')` callback, and Node runs that to completion
  without interleaving, so there is no lost-update window today. Worth remembering if any of
  those handlers ever becomes `async`.
- **`preStatus` grows with the number of notes.** Bounded by the archive size, not by traffic,
  and no longer served to anonymous callers (§15).
- **Sessions live in memory only.** A restart signs everybody out. That is a deliberate trade —
  no session store to secure, and the site is small enough that signing in again is cheap — but
  it is worth knowing before a deploy that restarts the process.
- **`Cache-Control: no-store` on every response, including static assets.** The app shell is
  ~750 KB and is re-fetched on every load. Correct-by-default for an archive where most paths
  can carry private content; revisit only with a per-route allowlist, never globally.
- **`/api/tree` re-walks the directories on every request.** The `data.txt` parsing and the
  grants file are memoised (§8), but the `readdirSync` walk itself is not. Measured at 39 ms
  for the merged EN+HU tree over 51 notes — fine now, worth revisiting an order of magnitude
  later.
